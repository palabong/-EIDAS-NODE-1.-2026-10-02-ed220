2. Information We Collect and Access

Project Bilanx — Credentials Hub operates under a strict data-minimization architecture split into two distinct contexts: (A) Authenticated Operator/Evaluator Sessions via Google Sign-In, and (B) Zero-PII Cryptographic Age-Gate Verification.

2.1 Google OAuth 2.0 User Data (Operator & Evaluator Authentication)

When you choose to sign in to Project Bilanx — Credentials Hub using Google Identity Services ("Sign in with Google"), our backend verifies the cryptographic JSON Web Token (ID Token) issued by https://accounts.google.com and accesses only the following basic OpenID Connect claims:

Data Element / Claim OAuth Scope Purpose of Collection
Google Subject Identifier (sub) openid Uniquely identifies the authenticated evaluator/operator session and binds security audit records.
Email Address & Verification Status (email, email_verified) email Displays the verified operator identity in the dashboard header and records accountable access logs.
Display Name & Profile Avatar URL (name, picture) profile Renders the active user badge within the authenticated application interface.
Technical Request Context (ipAddress, userAgent, timestamp) HTTP Transport Protects the node against unauthorized access, replay attacks, and maintains the security audit trail.

2.2 Zero-PII Consumer Cryptographic Verification (DK-SVS & Scheme B2)

For retail and age-restricted compliance workflows within the Dual-Key Sovereign Validation System (DK-SVS), zero consumer Personally Identifiable Information (PII) is transmitted or stored:

  • Key 1 (Institutional Binding): Verifies authentic product or relying-party metadata using ECDSA P-256 signatures.
  • Key 2 (Consumer Age-Gate): Evaluates a fixed 1,355-byte binary payload comprising Pedersen commitments on P-256 with a Nothing-Up-My-Sleeve (NUMS) generator and an 8-bit Non-Interactive Zero-Knowledge Proof (NIZKP Scheme B2) proving age ≥ 18 without revealing date of birth, full name, or national identification numbers.
  • FIDO2 / WebAuthn Assertions: Stores only public key credentials, key IDs, and monotonic signature counters to prevent credential cloning and replay.

3. How We Use Your Information

We process the data described above strictly for the following operational purposes:

  1. Cryptographic Authentication & Session Management: Validating Google ID tokens via Google's public certs and issuing an encrypted, short-lived session token (bilanx_sid HTTP-only cookie with a 4-hour time-to-live).
  2. Security & Compliance Auditing: Recording authentication events (LOGIN_SUCCESS, LOGIN_FAILURE, LOGOUT, COMPLIANCE_RUN) in our local access log database to demonstrate regulatory accountability under eIDAS 2.0 and customs compliance directives.
  3. Abuse & Replay Prevention: Enforcing single-use cryptographic nonces, challenge TTLs, and rate limits across verification endpoints.

4. Data Sharing, Third-Party Disclosure & Prohibitions

We treat all Google user data and security logs with strict confidentiality:

  • No Sale of Personal Data: We never sell, rent, lease, or trade Google user data or personal information to any third party.
  • No Advertising or Profiling: We never use Google user data for targeted advertising, retargeting, data brokering, or creditworthiness evaluation.
  • No AI/ML Foundation Model Training: Google user data obtained via OAuth 2.0 is never used to train, fine-tune, or improve generalized artificial intelligence or machine learning models.
  • Infrastructure Sub-processors: The application is hosted on secure cloud infrastructure (Google Cloud Run / Google AI Studio / Google Cloud Firestore in European regions and/or Fly.io Frankfurt fra region) acting solely as infrastructure processors under strict data protection terms.

5. Data Storage, Security & Retention

  • Session Lifespan: Authenticated sessions expire automatically after 4 hours or immediately upon clicking "Sign out".
  • Browser Local Storage: For user convenience during active evaluation, session metadata and sandbox simulation state are stored in your browser's localStorage (e.g., bilanx_verified_google_user, credentials_hub_profile) and are purged upon sign-out.
  • Audit Log Retention: Server-side access logs are capped at a rolling maximum of 10,000 events and retained only as needed for security verification and audit demonstration, after which they are automatically rotated or purged upon administrative request.
  • Cryptographic Safeguards: All network traffic is enforced over HTTPS/TLS, cross-origin requests are restricted by strict CORS and Content Security Policy (CSP) headers, and institutional assertions are signed with ECDSA P-256 keys.
